# VM 指令分发与本机栈

`runFrameLoop()` 推进 Zeus 调用帧，`execute()` 只负责分发指令。
指令实现按功能放在 `ZeusRunner/Dispatch/`，在 `VM` 类内引入。

每个指令处理函数都保留 `ZEUS_VM_NOINLINE` 边界。发布构建启用
`/GL /LTCG`，如果重新内联为一个巨型 switch，不同指令中的临时对象
会重新占据同一函数的本机栈帧，简单指令也必须承担整个函数的栈开销。

## 运算符调用流程

```zeus
let first = b"ab"[0];
let joined = b"ab" + b"cd";
```

这两种运算由 `impl bytes` 的运算符实现处理：

1. 指令处理函数查找运算符，创建闭包，将参数复制并保留到 VM 栈。
2. 返回待执行的 `CALL_CLOSURE` 指令，退出当前处理函数，释放其临时对象。
3. `execute()` 在循环中处理该调用，创建 Zeus 调用帧。
4. 返回原来的 `runFrameLoop()`，由它执行运算符函数并处理返回或异常。

待执行指令不能保留处理函数局部变量的指针。调用参数必须已进入 VM 栈。
方法调用同样通过这个循环重分发，不再使用处理函数内部的跳转标签。

构造、析构、成员拦截等需要等待结果并继续处理的入口仍使用同步调用。
拆分后的指令处理函数让这些入口不再递归携带整个解释器的临时对象。

## 回归验证

在项目目录构建后运行：

```powershell
python ZeusZTest/run_vm_dispatch_stack_test.py
```

测试强制检查 Windows EXE 的栈保留为默认 1MB，覆盖 bytes 索引、拼接、
切片、256 层运算符递归、深层异常恢复、class 运算符和默认参数，
并检查没有遗留的临时栈探针输出。

2026-10-16，MSVC x64 `/O2 /GL /LTCG` 最终 EXE 的展开信息显示：

| 函数 | 固定本机栈占用 |
| --- | ---: |
| 修复前 `execute` | 508,296 字节 |
| 修复后 `execute` | 1,704 字节 |
| `execute_DICT_LOAD_VALUE` | 2,936 字节 |
| `execute_ADD` | 2,808 字节 |
| 最大的独立指令处理函数 | 5,000 字节 |

这些数字包含固定分配与保存寄存器，不包含被调用函数的栈占用。
原始 1MB EXE 运行新增回归会以 `0xC00000FD` 退出；修复后 17 项全部通过。
构建配置不再增加 `/STACK`。
